# Project Workflow

本ファイルは Tab Manager Ex の開発手順を定める。
すべての Track は本ファイルに従う。

## 基本原則

1. 計画が単一の真実である。すべての作業は Track の `plan.md` で管理する。
2. 技術スタックの変更は実装の前に `tech-stack.md` へ記録する。
3. テスト駆動開発は機能変更に適用する。設定値の変更と文書の変更は対象外とする。
4. カバレッジは計測するが、数値ゲートを設けない。
5. ユーザー体験を優先する。IDE の標準操作に存在しない操作だけをユーザーが個別に叩けるようにする。
6. 非対話型のコマンドを優先する。継続的インテグレーションでは `CI=true` を設定して監視モードを無効にする。

## タスクワークフロー

すべてのタスクは次の順序に従う。

### 標準タスクワークフロー

1. タスクを選ぶ。`plan.md` を先頭から読み、次に行うタスクを 1 つだけ選ぶ。
2. 進行中に記録する。`plan.md` の対象タスクを `[ ]` から `[~]` に変更してから作業を始める。
3. 失敗するテストを書く（Red）。
   - 機能変更、または不具合修正の場合にのみ行う。
   - 設定値の変更と文書の変更では、この工程を省略してよい。
   - テストを実行し、期待どおり失敗することを確認する。失敗を確認するまでは次へ進まない。
4. テストを通す実装を書く（Green）。
   - 失敗したテストを通すために必要な最小限のコードだけを書く。
   - テストを再実行し、すべて通ることを確認する。
5. リファクタリングを行う（任意）。
   - テストが通っている状態で、外部の振る舞いを変えずに実装とテストを整理する。
   - 変更後にテストを再実行する。
6. カバレッジを計測する。Kover のレポートが生成されることを確認する。数値の合否判定は行わない。
7. 逸脱を記録する。実装が `tech-stack.md` や `code_styleguides/` の前提と異なった場合は、実装を止めて `tech-stack.md` を更新してから再開する。
8. 変更をコミットする。
   - 変更したファイルは個別に `git add <file>` でステージする。`git add .` と `git add -A` は禁止する。
   - ステージの前後に `git diff` を確認し、意図しない変更が含まれていないことを確認する。
   - コミットメッセージは [コミット規約](#コミット規約) に従う。
9. タスクサマリーを git notes に付ける。
   - コミットハッシュを `git log -1 --format="%H"` で取得する。
   - タスク名、変更内容の要約、作成または変更したファイルの一覧、変更の目的を書く。
   - `git notes add -m "<内容>" <コミットハッシュ>` で添付する。
10. plan.md にコミット SHA を記録する。対象タスクを `[~]` から `[x]` に変更し、コミットハッシュの先頭 7 文字を付ける。
11. plan.md の更新をコミットする。メッセージは `chore: タスク '<タスク名>' を完了とする` とする。

### タスクの訂正と計画の修正

実装済みのタスクやフェーズに訂正が必要な場合は、次の手順で計画の整合性を保つ。

1. 進行中の調整。タスクが `[~]` の間に軽微な不足が見つかった場合は、現在の作業の流れで直接修正し、テストを通してからコミットする。
2. コードレビューによる訂正。レビューで問題が指摘された場合は `conductor-review` を使う。レビューは自動的に `plan.md` へ `Review Fixes` フェーズを追加する。訂正タスクは正式に追跡とチェックポイントの対象になる。
3. 論理的な巻き戻し。タスクの実装が根本的に誤っている場合は `conductor-revert` を使う。関連コミットを `git revert` し、`plan.md` の状態を `[ ]` に戻してやり直す。

### フェーズ完了時の検証とチェックポイント

フェーズを構成する最後のタスクが完了した直後にこの手順を実行する。

1. 開始を宣言する。フェーズが完了したことと、検証とチェックポイントの手順に入ることをユーザーに伝える。
2. フェーズの変更範囲を求める。
   - `plan.md` から前のフェーズのチェックポイント SHA を読む。チェックポイントが無い場合は最初のコミット以降のすべての変更が対象である。
   - `git diff --name-only <前のチェックポイント SHA> HEAD` で対象ファイルを列挙する。
   - 拡張子が `.md`、`.yml`、`.properties`、`.xml` のファイルはコードではないため除外する。
   - 残った各ファイルに対して、対応するテストファイルが存在するかを確認する。無い場合は作成する。作成前にリポジトリ内の他のテストの命名規則と記法を読み、本文の規約に従う。
3. 自動テストを実行する。実行前に必ず宣言する。
   - `./gradlew check` を実行する。テスト、Detekt、Kover をまとめて実行する。
   - 失敗した場合はユーザーに報告し、デバッグを開始する。修正案は最大 2 回まで提案できる。2 回提案しても失敗する場合は停止し、事実を報告してユーザーに指示を求める。
4. 手動検証計画を提示する。
   - `product.md`、`product-guidelines.md`、`plan.md` を読み、フェーズが目的とするユーザーの目標を確認する。
   - 手順と期待結果を含む検証計画を段階的に提示する。
   - IntelliJ プラグインの検証では `./gradlew runIde` で起動した実 IDE を使う。
5. ユーザーの明示的な承認を待つ。検証計画を提示したら、成功か変更箇所の指摘かを求めて停止する。明示的な承認なしに次へ進まない。
6. レポート対象のコミットを特定する。チェックポイント用の空コミットは作らず、フェーズ中最後の機能コミットを使う。
7. git notes で監査可能な検証レポートを付ける。自動テストのコマンド、手動検証の手順、ユーザーの承認を記載する。
8. plan.md にチェックポイント SHA を記録する。フェーズの見出しに `[checkpoint: <SHA 先頭 7 文字>]` を付ける。
9. plan.md の更新をコミットする。メッセージは `chore: フェーズ '<フェーズ名>' を完了とする` とする。
10. 完了を宣言する。チェックポイントと git notes の検証レポートの内容を報告する。

## 品質ゲート

タスクを完了とする前に次を確認する。

- `./gradlew test` が成功する
- `./gradlew detekt` が違反 0 件で成功する
- `./gradlew verifyPluginProjectConfiguration` が成功する
- 1 行の長さが 120 文字を超えない
- 未使用の import が残っていない
- 秘密情報がソースへ含まれていない
- `CHANGELOG.md` の更新が必要なら行われている
- 機能がユーザーの目に触れる変更なら、手動検証とユーザーの承認が完了している

## 開発コマンド

以下のタスク名は `./gradlew tasks --all` で確認した実在組である。

Windows では `gradlew.bat` を使う。

### セットアップ

```bash
# ツールチェーンの自動解決により JDK の手動設定は不要
./gradlew wrapper
```

### 日常の開発

```bash
# プラグインの配布物を生成する
./gradlew buildPlugin

# プラグインを組み込んだ IDE を起動する
./gradlew runIde

# テストを実行する
./gradlew test

# テスト、Detekt、Kover をまとめて実行する
./gradlew check

# 静的解析を実行する。build.gradle.kts で autoCorrect が有効
./gradlew detekt

# 設定の妥当性を検証する
./gradlew verifyPluginProjectConfiguration

# Plugin Verifier でバイナリ互換性を検証する
./gradlew verifyPlugin

# プラグイン構造を検証する
./gradlew verifyPluginStructure

# 署名を検証する
./gradlew verifyPluginSignature
```

`build.yml` のヘッダコメントにある `runPluginVerifier` というタスクは存在しない。正しい名前は `verifyPlugin` である。

### コミット前

```bash
./gradlew check
./gradlew verifyPlugin
git status --porcelain
git diff --cached
```

### UI テスト

```bash
# robot サーバ込みで IDE を起動する。ポート 8082 を使う
./gradlew runIdeForUiTests
```

`.github/workflows/run-ui-tests.yml` の `java-version` は 17 である。プラグインの `jvmToolchain(21)` と一致していないため、実行前に 21 へ変更する必要がある。

## テスト要件

### 単体テスト

- 設定値の変更と文書の変更には単体テストを書かない。
- 機能追加と不具合修正には単体テストを書く。
- IntelliJ Platform のテスト基盤を使う。`testFramework(TestFrameworkType.Platform)` が設定済みである。
- 成功経路と失敗経路の両方を検証する。
- 外部依存をモックで置き換える。`FileEditorManager` と `FileEditorManagerEx` は実 IDE なしでは動作しないため、`TestApplicationManager` を使うかサービス層を抽象化して差し替える。

### 統合テスト

- 3 つのアクションそれぞれについて、実行結果が期待どおりかを確認する。
- Git ログのコンテキストメニューからの起動を実際の Git リポジトリで確認する。

### 手動検証

- すべての機能変更で `./gradlew runIde` による実 IDE での確認を行う。
- 結果を GitHub Issue のコメントに記録し、ユーザーの明示的な承認を得る。

## コードレビュー手順

### 自己レビュー

1. 機能
   - 仕様どおり動作する
   - エッジケースが扱われている
   - ファイルが存在しない場合に例外を出さない
2. コード品質
   - `code_styleguides/architecture_rules.md` の依存方向を守っている
   - アクションが `application/` のサービスへ委譲している
   - 命名が `product-guidelines.md` の規約に一致する
   - コメントは英語で書いてある
3. テスト
   - 必要なテストが書かれている
   - テストが通る
4. セキュリティ
   - 秘密情報がハードコードされていない
   - 署名用の証明書と鍵がコミット対象に入っていない
5. IntelliJ Platform 固有
   - `getActionUpdateThread()` が `ActionUpdateThread.BGT` を返している
   - EDT が必要な処理に `@RequiresEdt` が付いている
   - write アクセスを EDT 外で行っていない

## コミット規約

Conventional Commits を採用する。形式は次のとおり。

```text
<type>: <日本語での説明（50文字以内）>

[本文（任意）]

ref: <Issue 番号>

[Co-Authored-By: {AI}]
```

- スコープは付けない。
- タイトルと本文は日本語で書く。
- タイトルだけで内容が分からない場合は、本文に何を達成するための実装かを箇条書きで書く。
- Issue 番号はブランチ名の先頭の数字である。
- type は `feat`、`fix`、`refactor`、`style`、`docs`、`test`、`chore` のみを使う。
- `Co-Authored-By` は任意である。付与する場合は `{AI}` を使う。`{AI}` はプレースホルダーであり、実行する AI エージェントのシステム設定に識別子が記載されている場合にのみ付与する。
- システム設定に識別子の記載がない場合は署名を付けない。他のエージェント名を推測で記載してはならない。

### 例

```text
feat: IntelliJ 2026.3 に対応

- until-build を削除し、2026.3 以降の IDE でもプラグインが利用できるようにした

ref: 124

Co-Authored-By: {AI}
```

## 完了の定義

タスクは次を満たしたときに完了とする。

1. 仕様どおりの実装を終えている
2. 必要な単体テストが書かれ、通っている
3. `./gradlew check` が成功する
4. `./gradlew verifyPlugin` が成功する
5. 必要な文書が更新されている
6. 機能がユーザーの目に触れるなら、手動検証とユーザーの承認が完了している
7. 適切なメッセージでコミットされている
8. git notes にタスクサマリーが付いている

## 緊急時の手順

### 本番での重大な不具合

1. main から修正ブランチを切る
2. 不具合の再現テストを書く
3. 最小限の修正を入れる
4. `./gradlew check` と `./gradlew verifyPlugin` を実行する
5. 修正をマージしてリリースを構成する
6. 内容を GitHub Issue に記録する

### 署名鍵の漏洩

1. まず JetBrains Marketplace の管理画面から公開中のバージョンを取り下げる
2. 新しい鍵対を生成する
3. 証明書チェーンと鍵を環境変数へ設定し直す
4. 漏洩した鍵と証明書を Git の履歴から除去する
5. 影響を受けたバージョンを再リリースする

## リリース手順

### リリース前の確認

- `./gradlew check` が成功する
- `./gradlew verifyPlugin` が成功する
- `CHANGELOG.md` の `[Unreleased]` にリリース内容を記載している
- `pluginVersion` を SemVer で更新している

### リリースの流れ

1. 機能ブランチを main へマージする
2. `.github/workflows/build.yml` がリリースの下書きを作る
3. 人が下書きの 내용을レビューして公開する
4. `release` イベントが発生し、`release.yml` が起動する
5. `release.yml` が `patchChangelog` を実行し、`CHANGELOG.md` を更新する PR を作る
6. 人がその PR をマージする

手順 6 を省略すると `CHANGELOG.md` がリリース内容とずれる。過去のリリースで一度この事故が起きている。

### リリース後

- Marketplace 上の Plugin Verifier の結果を確認する
- Issue を閉じる
- ユーザーからのフィードバックを記録する

## 継続的改善

- 遭遇した痛点ごとに本ファイルを更新する
- 更新の理由を `tech-stack.md` または Git のコミットメッセージに記録する
- simplicity と保守しやすさの原則を維持する
